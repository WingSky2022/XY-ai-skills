# File Architect — 文件架构规范生成器

把「文件该怎么放、该怎么命名、AI 怎么找到它」从口头约定固化成可落地的规范文件。本技能的知识底座是对六大主流文件架构体系的横向调研（见 `references/research-report.md`），核心结论只有一句：**高手们的结构高度趋同**——一级目录 7±2 个、嵌套不超三层、文件名承载时间与版本、收集箱定期清空、归档只进不改。

## 何时使用

触发场景：

- 新项目 / 新工作区开张，需要一套目录骨架和命名规则
- 现有目录"能跑但很乱"，需要体检 + 渐进整改
- 知识库（Obsidian / 笔记库）该按什么逻辑组织
- 需要给 AI 写导航层（CLAUDE.md / AGENTS.md 路由表、目录 README）
- 团队要统一命名规范，避免"最终版 / 终极版 / 真的最终版"

不适用：单纯的文件批量改名/移动（属于文件操作，不是架构设计）；单个文档的排版整理。

## 核心心智模型：三个问题定架构

设计任何文件架构，先回答这三问，顺序不能反：

1. **「下次要用它时，我会去哪找？」** —— 决定第一分类维度。按"什么时候用"（项目/责任/参考/归档）切分优于按"这是什么"（学科/格式）切分，因为后者要求用户先想清楚本体论，成本高。
2. **「谁来找？只有人，还是 AI 也要找？」** —— 决定是否需要 AI 导航层。AI 找文件不走肌肉记忆，只走索引与路由表。
3. **「这个文件一年后还有用吗？」** —— 决定归档策略。有用且会变 → 活跃区；有用但不变 → 归档只进不改；没用 → 收集箱，定期清。

## 六大体系速查（选型用）

| 体系 | 一句话内核 | 什么时候选它 | 代表结构 |
|:---|:---|:---|:---|
| **PARA** | 按可操作性分四桶 | 项目驱动型工作，通用文件与笔记混放 | Projects / Areas / Resources / Archives |
| **AI 原生 PARA** | PARA + 系统前缀目录 + 铁律 | 需要 AI 参与读写文件（本技能默认推荐） | 00_Inbox … 06_Metadata |
| **Johnny.Decimal** | 编号即坐标，两层封顶 | 文件极多（数千+），需要口头"报坐标" | `13.55` 形式，10 Area × 10 Category |
| **Kepano 极简库** | 反文件夹树，靠链接与属性 | 思考型笔记库，一篇笔记属于多个主题 | 一级 7 个目录 + 属性视图 |
| **Zettelkasten + MOC** | 原子笔记 + 双链 + 内容地图 | 深度学习、研究、写作 | 00_Inbox → 01_文献 → 02_Zettel → 03_MOC |
| **CPDX 元数据命名法** | 文件名即元数据 | 工作文档命名（与上述体系正交，可叠加） | `(2024-03-01)-01-标题(v2)#已批准@产品部` |

**关键判别**：文档协作库适合文件夹树，思考型笔记库适合链接网，两者**不要混用同一套逻辑**。同一个工作区既要存文档又要记思考时，分两个根目录，不要强行统一。

## 十条约会数原则（任何方案都必须满足）

这十条是六大体系的最大公约数，生成方案后逐条自检：

1. **一级目录 7±2 个**，用编号前缀锁定排序，让位置形成肌肉记忆
2. **嵌套不超过 3 层**，更深的层级说明分类维度选错了
3. **收集箱是唯一允许乱的地方**，且每周强制清空
4. **每个文件只有一个权威位置**，跨场景用引用而非副本
5. **文件名 = 时间 + 主题 + 版本**，日期用国际标准格式（`YYYY-MM-DD`），版本禁用"最终版"
6. **归档只进不改**：项目结束当天整目录移走、不改名，历史始终可搜索
7. **给 AI 写导航**：每个目录一份说明 + 根级触发词路由表，AI 开工先读索引
8. **附件与文本分离**：二进制文件集中存放，不混在知识文件里
9. **决策与教训单独建档**：AI 长期记忆中最值钱的部分，避免重复踩坑
10. **渐进迁移**：不追求 100% 合规，先保证高频文件与新文件合规，旧文件摸到再改

## 工作流程

### 第 1 步：摸清现状（有目录时必做）

对已有工作区，先跑审计脚本拿到事实，不要凭感觉下结论：

```bash
python3 scripts/audit_tree.py "<目标目录>" 
```

输出四类问题：嵌套超限、命名违规、收集箱堆积、缺失目录说明文件。加 `--json` 取机器可读结果，`--max-depth N` 调阈值。

无既有目录（全新项目）→ 跳过，直接进第 2 步。

### 第 2 步：定基座

按「三个问题」选型，产出**一句话架构声明**，例如：

> 本工作区为项目驱动 + AI 协作型，采用 AI 原生 PARA 作为基座，叠加 CPDX 命名规则；一级目录 7 个，嵌套封顶 3 层。

选型参考：

| 场景 | 推荐基座 | 关键增量 |
|:---|:---|:---|
| 通用项目 / 客户交付 | AI 原生 PARA | 00–06 前缀目录 + 每目录 README |
| 文件量极大（数千+），多人协作 | Johnny.Decimal | 编号坐标 + 单一 ID 字段 |
| 个人笔记 / 思考库 | Kepano 极简 + 属性视图 | 一级扁平 + 双链，不建深树 |
| 研究 / 学习 / 写作 | Zettelkasten + MOC | 文献笔记 → 原子笔记 → 内容地图 |
| 团队合规文档 | AI 原生 PARA + CPDX | 标签/责任人后缀 + 审批态标记 |

### 第 3 步：生成目录骨架

输出完整目录树（含每层的用途与"什么不该放这里"）。默认骨架见 `references/templates.md`，按场景裁剪，**不要照抄**——一级目录一旦超过 9 个就说明没有做取舍。

目录名硬性规则：

- 统一小写 + 下划线或短横线二选一，**路径永不带空格**（AI 与脚本零转义问题）
- 编号前缀两位数字（`00_`、`01_`），保证排序稳定
- 目录名表达"这里放什么"，不表达"这是第几批"

### 第 4 步：定命名规则

给出**可被判定的**规则，而非"要清晰"这类空话。默认规则：

```
YYYY-MM-DD_项目_描述_v{主}.{次}.{修}.{扩展名}
```

配套判定表（写进交付物，供日后自查）：

| 写法 | 判定 | 原因 |
|:---|:---:|:---|
| `2026-10-21_客户A_需求说明书_v1.2.docx` | ✅ | 时间可排序、主题明确、版本可递增 |
| `2026-10-21_客户A_需求说明书_v1.2_已批准.docx` | ✅ | 状态作为后缀，不挤占版本位 |
| `需求说明书-最终版.docx` | ❌ | 无时间、版本不可排序 |
| `需求说明书-最终版2-真的最终.docx` | ❌ | 同上，且无法程序化判定新旧 |
| `需求 说明书.docx` | ❌ | 含空格，脚本与 AI 处理需转义 |
| `2026.10.21_需求.docx` | ⚠️ | 日期格式非国际标准，跨系统排序会错 |

版本号永远紧跟标题，使同项目不同版本自然相邻。多人协作可选后缀：`#标签` 标状态、`@责任人` 标归属。

### 第 5 步：写 AI 导航层（本技能的核心增量）

这是多数规范缺失的一层。交付三件套：

**① 根级主控文件**（`CLAUDE.md` / `AGENTS.md` / `README.md`，按生态选），只写三样东西：

```markdown
## 目录索引
| 目录 | 放什么 | 不该放什么 |
|:---|:---|:---|
| 00_Inbox/ | 未分类新文件，每周清空 | 任何存活超过 7 天的文件 |

## 触发词路由表
| 用户说到 | 去读 |
|:---|:---|
| 项目进度 / 交付节点 | 01_Projects/<项目名>/概览.md |
| 历史决策 / 为什么这么定 | 06_Decisions/ |

## 使用规则
- 写入前先读本目录 README
- 只写指针与红线，流程封装到独立文件
```

**② 每个非叶子目录一份 `README.md`**：写明"这里放什么、当前状态、最后更新"。AI 进目录先读它。

**③ 决策存档目录**：规范变更、技术选型单独立档，一条决策一个文件，含"背景 / 选项 / 结论 / 日期"。这一层是 AI 长期记忆中最值钱的部分。

> 铁律：主控文件**只写指针与红线**，不要把整份规范抄进去——它会随会话被反复加载，臃肿即噪音。仓库结构本身就是最根本的提示词。

### 第 6 步：渐进迁移计划

不要一次性大搬家。按四阶段推进（源自 Johnny.Decimal 社区的七千条笔记迁移实践）：

1. **只读扫描**：跑 `audit_tree.py`，摸清分布，不动任何文件
2. **搭骨架**：建新目录 + README + 主控文件，此时旧文件原地不动
3. **新文件强制合规**：新产生的文件一律进新骨架，按新命名
4. **旧文件摸到再改**：谁动过谁顺手迁移，每周留 15 分钟做清理

### 第 7 步：验收自检

交付前逐条确认：

- [ ] 一级目录数量在 7±2 范围内
- [ ] 全树嵌套 ≤ 3 层（`audit_tree.py` 验证）
- [ ] 每个非叶子目录有 README
- [ ] 根级主控文件含目录索引 + 触发词路由表 + 使用规则三段
- [ ] 命名规则可程序化判定（有明确的正则或判定表）
- [ ] 收集箱清空周期已约定（建议每周）
- [ ] 归档目录标注"只进不改"
- [ ] 附件目录独立于文本目录

## 交付物清单

一次完整交付包含：

```
<目标工作区>/
├── CLAUDE.md 或 AGENTS.md    # 根级主控：目录索引 + 触发词路由 + 使用规则
├── 00_Inbox/README.md        # 收集箱说明（含清空周期）
├── 01_Projects/README.md     # 各一级目录说明
├── ...
└── <规范正文>                 # 命名规则 + 判定表 + 迁移计划
```

## 配套资源

- `scripts/audit_tree.py` —— 目录体检脚本，输出四类问题，支持 `--json` / `--max-depth`
- `references/templates.md` —— 目录骨架模板、目录 README 模板、主控文件模板
- `references/research-report.md` —— 六大体系调研原始报告（选型存疑时查此，不必每次通读）

## 常见反模式

| 反模式 | 症状 | 修法 |
|:---|:---|:---|
| 分类维度混用 | 同一层既有"客户"又有"合同" | 只保留一个维度，另一种降为标签 |
| 深树成瘾 | 5 层目录，每层 2 个文件 | 砍到 3 层，多余维度改用命名前缀 |
| 归档可改 | 归档目录里文件还在被编辑 | 改为只读，改动走"取出→改→重新归档" |
| 导航层臃肿 | CLAUDE.md 上千行 | 只留指针与红线，细节下沉到目录 README |
| 完美主义迁移 | 要一次性全改完，结果半途而废 | 换渐进策略，先新文件后旧文件 |
| 人类直觉词做目录名 | `重要/紧急/其他` | 改为可判定的客观维度（时间、状态、归属） |
